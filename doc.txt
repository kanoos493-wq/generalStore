MASTER PROJECT SPECIFICATION: OFFLINE-FIRST GENERAL STORE MANAGEMENT & POS ANDROID APP
1. Your role and mission

Act as a senior Android application architect, React Native engineer, database engineer, inventory/accounting specialist, UI/UX designer, QA engineer, and DevOps engineer.

Build a complete, production-minded Android mobile application for managing a general store, grocery shop, kiryana store, mini-mart, or small retail business in Pakistan.

This must be a real, functional application—not a UI mockup, clickable prototype, demo dashboard, or collection of nonfunctional screens.

The application must work completely offline after installation. Core functionality must never require an internet connection, online account, cloud database, Firebase, remote API, or paid build service.

Project priorities, in order:

Correct inventory, sales, purchases, accounting, and ledger calculations.
Reliable offline operation and protection against data loss.
Fast performance on budget Android devices.
Simple, touch-friendly workflows for daily shop operations.
Urdu and English support, including right-to-left layouts.
Secure PIN protection, backup, restoration, and optional encryption.
Reproducible APK generation through GitHub Actions.

Do not stop after creating a plan or design. Inspect the repository, create the application, implement features, test it, and produce a working APK through GitHub Actions.

If the repository is empty, initialize the project. If an existing project is present, inspect it and preserve useful working code.

Do not ask me to install Android Studio. Do not use Expo Application Services (EAS) or any Expo cloud build service. Do not make Android Studio a prerequisite for my local development workflow.

2. Required technology stack

Use the following architecture unless a verified technical incompatibility makes a specific choice impossible. If you change a component, document why and select a compatible alternative before implementing it.

Mobile framework: React Native with TypeScript.
Android project: React Native Community CLI with the native Android project committed to Git.
Android build: Gradle wrapper and a compatible JDK/Android SDK configured in GitHub Actions.
Local database: SQLite, accessed through a maintained native SQLite integration supporting prepared statements, transactions, indexes, migrations, and appropriate native performance.
Database encryption: SQLCipher or an equivalently maintained, verified encryption solution. Never claim the database is encrypted if it is not.
State management: a lightweight, typed state management solution such as Zustand.
Forms and validation: React Hook Form with a schema validation library such as Zod.
Navigation: React Navigation.
Sensitive secrets: Android Keystore-backed secure storage, using a maintained native integration.
Printing: native Android Bluetooth/USB/network printing integration as supported by the device and selected printer.
Testing: unit tests, database integration tests, inventory/accounting tests, and React Native component tests.
Build automation: GitHub Actions using a committed Gradle wrapper and pinned, compatible toolchain versions.

Choose maintained dependencies with compatible licenses and Android support. Avoid unnecessary libraries, excessive abstraction, giant UI frameworks, and dependencies that require a permanent network connection.

The installed app must not contain mandatory analytics, advertisements, tracking, cloud authentication, or background network synchronization.

3. Offline-first architecture

The local database is the source of truth.

All core operations must work in airplane mode, including:

Opening the app and dashboard.
Creating, editing, searching, and viewing products.
Recording purchases and purchase returns.
Making sales and printing or previewing bills.
Recording cash, digital, credit, and partial payments.
Customer and supplier profiles.
Customer and supplier khata ledgers.
Inventory adjustments and stock counts.
Low-stock tracking and restock planning.
Daily expenses and cash closing.
Reports and exports.
PIN management, settings, backups, and restoration.
Accessing historical invoices and transaction details.

Never silently discard a transaction because a device loses connectivity.

Do not use a remote database as a fallback or dependency. The app should not require registration, an internet connection, or a server to start.

Separate business logic, database access, UI, printing, and backup services into well-defined modules. Keep UI components independent from SQL implementation details.

Provide a database migration system with schema versions, transaction-safe upgrades, and backup-before-risky-migration safeguards.

Critical inventory unit and packaging engine

Implement a robust unit-conversion engine. This is a core requirement, not an optional feature.

Use a canonical stock quantity per product, expressed in the smallest practical supported base unit. Use exact decimal arithmetic or scaled integer quantities wherever appropriate. Do not use ordinary binary floating-point arithmetic for financial calculations.

Each product must support:

One base stock unit.
Multiple purchase units.
Multiple sale units.
Independent conversion factors.
Configurable decimal precision.
Fractional purchase quantities.
Fractional sale quantities where physically meaningful.
Correct stock conversion regardless of which unit was used in a transaction.

A packaging hierarchy must support multiple levels.

Example A: Sugar or flour

Base unit: kg.
Base selling price: PKR 150 per kg.
Upper unit: bag.
One bag contains 10 kg.
Calculated selling price per bag: PKR 1,500.
Purchase cost per bag: PKR 1,200.
Calculated purchase cost per kg: PKR 120.
Estimated gross profit per full bag, before other costs: PKR 300.

The product form should let the user set the selling price per kg and calculate the bag price automatically. It must also let the user record purchases by bag, kg, or mixed quantities.

Example B: Selling partial quantities

If the customer buys 500 g of sugar:

Quantity sold: 500 g.
Canonical stock deducted: 0.5 kg.
Sale price: PKR 75 at the configured PKR 150/kg price.
Bill displays the correct unit and amount.

Also support 100 g, 250 g, 750 g, 1.25 kg, and other valid quantities.

Example C: Pieces, boxes, and cartons

Base unit: piece.
Selling price per piece: PKR 20.
One box contains 6 pieces.
One carton contains 20 boxes.
One carton therefore contains 120 pieces.
Selling price per box: PKR 120.
Selling price per carton: PKR 2,400.
Purchase cost can be entered per carton, box, or piece.

The product form must let the user define both box and carton packaging independently, including their conversion factors.

Example D: Mixed purchase quantities

A purchase can contain:

4 cartons.
10 boxes.
4 individual pieces.

For the above product, the total is 4 × 120 + 10 × 6 + 4 = 544 pieces.

The system must record 544 pieces in stock and preserve the quantities and prices entered on the original purchase.

Example E: Partial packages and mixed stock

Allow purchases such as:

4 bags and 4 kg.
2.5 bags.
3 cartons, 2 boxes, and 5 pieces.
Any valid combination of configured purchase units.

Do not force a purchase into whole bags or cartons.

Price and cost handling

Maintain separate values for:

Purchase unit price.

Derived selling prices should be calculated automatically from the configured base selling price and conversion factor, with rounding rules stated and applied consistently. Allow an authorized manager to override a derived price if desired.

Do not overwrite historical transaction prices when a product's current price changes.

A new purchase may change the current cost estimate, but it must not silently change the selling price unless the manager explicitly enables a price-update rule.

When a purchase is recorded by bag or carton, calculate its effective base-unit cost and show the expected margin and gross profit at current selling prices.

For example, if a 10 kg bag costs PKR 1,200 and the selling price is PKR 150/kg, show:

Distinguish gross margin from markup. Label estimated profit correctly and do not represent it as final net profit.

20. PIN security and automatic app lock

Security is a mandatory feature.

On first launch, require the manager to set a PIN before accessing business data.

Requirements:

Support a configurable numeric PIN of a sensible minimum length.
Store a salted, computationally expensive PIN verifier using an appropriate password-hashing algorithm, not a plaintext PIN or reversible PIN.
Never log or export the PIN.
Unlock the app after correct verification.
Automatically lock after configurable inactivity intervals such as 30 seconds, 1 minute, 5 minutes, 10 minutes, 15 minutes, or never, if explicitly allowed by the security policy.
Default to a sensible secure timeout.
Also lock when the app returns from the background after the configured timeout.
Reset the inactivity timer on appropriate user interaction.
Obscure sensitive content when the app is backgrounded, where supported.
Rate-limit failed PIN attempts and apply an appropriate increasing delay.
Do not lock or terminate an in-progress database transaction halfway through.
Require reauthentication for sensitive manager actions where configured.
PIN change and recovery

Changing the PIN must require the current PIN.

For forgotten-PIN recovery, support a secure recovery flow based on recovery questions selected from a list, if the manager enables that method.

At setup, let the manager select multiple questions and provide answers. Store normalized answer verifiers securely, not plaintext answers. Do not display the saved answers later.

Possible questions:

What was the name of your first school?
What was the name of your first teacher?
What was the name of your childhood best friend?
In which city were you born?
What was the name of your first pet?
What was the name of a memorable childhood place?
What was the name of your favourite childhood game?
What was a memorable gift you received as a child?
What was the name of your favourite childhood book?
What was a memorable family holiday destination?

Allow custom questions as well.

Require more than one recovery answer, enforce attempt limits, and do not reveal whether a specific answer was correct before the full recovery attempt is validated.

Important security policy: recovery questions are weaker than strong authentication. Warn the manager about this risk and offer an alternative recovery method, such as a securely generated recovery code stored outside the device.

If PIN recovery cannot be completed, offer a carefully explained reset process that does not silently erase business data. Any destructive reset must require explicit confirmation and a warning about backup and data loss.

Do not create a hidden master PIN, universal bypass PIN, hardcoded recovery PIN, or plaintext secret.

Protect sensitive data using Android Keystore-backed encryption where applicable. If SQLCipher is used, design encryption-key creation, storage, backup, restoration, and recovery carefully. Never promise recovery of an encrypted database if the only encryption key has been irretrievably lost.
